# 三层记忆架构

RFQPilot 的 Agent 记忆分为三个物理层，长期数据不再写入本地 SQLite：

| 层级 | 存储 | 保存内容 | 是否权威 |
|---|---|---|---|
| 短期记忆 | SQLite | 当前会话工作台、字段来源、待确认项、有限轮次历史与摘要 | 是（会话范围） |
| 结构化长期记忆 | MySQL | 原文、摘要、类型、租户/账号/项目范围、同意、状态、版本、TTL、删除作业和索引 Outbox | 是（长期范围） |
| 长期语义记忆 | Milvus | `memory_id`、范围字段、Embedding、模型版本和 MySQL 记录版本 | 否，可从 MySQL 重建 |

## 写入闭环

1. Agent 只把本轮状态写入 SQLite 短期工作台。
2. 客户记忆先进入 `pending_consent`，工作区记忆先进入 `pending_confirmation`。
3. 用户同意或操作人确认后，MySQL 事务把记录改成 `active`，并写入同库 Outbox。
4. 后台 Worker 消费 Outbox，用 `memory_id` 幂等写入或删除 Milvus 向量。
5. Milvus 失败不会回滚已经确认的 MySQL 事实；事件会重试，达到上限后进入死信状态。

## 召回闭环

1. MySQL 按租户、账号/操作人、项目、用途和状态产生关键词候选。
2. Milvus 在相同范围过滤下产生语义候选。
3. 两路候选用 RRF 融合。
4. 返回 Agent 前，再到 MySQL 检查同意、状态、版本、TTL 和会话范围。Milvus 中孤立或过期的 ID 不会被返回。

## 配置与初始化

复制 `.env.example` 后配置 `NANOCLAW_MEMORY_MYSQL_*`、`NANOCLAW_MEMORY_MILVUS_*`。生产语义检索应使用真实 Embedding；`local_hash` 仅用于本地连通性测试，不具备可靠语义质量。

MySQL 表会在首次启用长期记忆时幂等创建；也可以显式执行：

```text
agent/memory_runtime/migrations/001_long_term_memory.mysql.sql
```

Milvus 应先用管理令牌创建两个集合，再让应用切换到受限令牌：

```powershell
$env:NANOCLAW_MEMORY_MILVUS_ADMIN_TOKEN = "root:<管理密码>"
.\.venv\Scripts\python.exe -m agent.memory_runtime.milvus_admin
```

随后清除 `NANOCLAW_MEMORY_MILVUS_ADMIN_TOKEN`，并将 `NANOCLAW_MEMORY_MILVUS_TOKEN` 设置为受限应用账号的 `用户名:密码`。

## 故障边界

- MySQL 不可用：长期记忆读写失败关闭，不降级到 SQLite。
- Milvus 不可用：语义通道标记为降级；关键词通道仍由 MySQL 提供，且不会改用本地向量副本。
- Embedding 不可用：Outbox 保留并重试；MySQL 权威记录不丢失。
- SQLite 损坏：只影响对应会话的短期工作台，不改变已经确认的长期记录。
