# RAG 文本切分设计

> 当前产品知识入库使用 `trade_rag.token_chunking.TokenSplitter` 和随项目保存的 Qwen3-Embedding-8B tokenizer：父块 800 token、相邻正文父块重叠约 80 token（10%），子块 200 token、重叠 20 token。Markdown 表格先按表头和数据行拆分，PDF 表格先转换为 Markdown。下文的 `RecursiveSplitter` 字符级说明保留为历史设计和兼容接口，不代表当前产品知识库的切块单位。

## 1. 目标

文本切分器负责把原始文档转换成适合索引和检索的文本块，同时尽量保留自然语言结构、Markdown 代码块和相邻块之间的上下文连续性。

本设计采用：

- 从粗到细的递归分隔符栈
- 无可用分隔符时的字符级硬切
- Markdown 围栏代码块原子保护
- Markdown 标题与后续正文粘合
- 相邻块尾部字符重叠
- 父块与子块两级切分

设计目标是在“块足够小，便于精确召回”和“上下文足够完整，便于理解”之间取得平衡。

## 2. 在 RAG 链路中的位置

```mermaid
flowchart LR
    D[原始文档] --> P[父块切分]
    P --> C[对子块再次切分]
    C --> E[子块向量化]
    E --> I[写入 PostgreSQL / Milvus / Elasticsearch]
    I --> R[按子块召回]
    R --> B[回查父块上下文]
    B --> A[生成答案]
```

切分器不负责向量化、索引写入、检索或答案生成，只负责产生有序的 `Chunk` 列表。

## 3. 数据结构

单个切分结果使用以下结构：

```python
@dataclass
class Chunk:
    id: int
    content: str
```

字段含义：

- `id`：本次切分结果中的顺序编号，从 `0` 开始连续递增。
- `content`：文本块正文。

`Chunk.id` 是切分阶段的局部序号，不应被当成数据库全局主键。入库后应使用 PostgreSQL 生成的 `pg_id` 关联 Milvus、Elasticsearch 和正文记录。

## 4. 配置与参数规范化

默认配置：

```yaml
rag:
  chunk_size: 200
  chunk_overlap: 50
```

初始化时执行以下规范化：

```text
chunk_size = max(1, chunk_size)
chunk_overlap = max(0, chunk_overlap)

如果 chunk_overlap >= chunk_size：
    chunk_overlap = chunk_size - 1
```

这样可以避免零长度块、负重叠以及 overlap 不小于块大小导致的异常行为。

需要注意：`chunk_size` 和 `chunk_overlap` 都按 Python 字符串长度计算，不是模型 Token 数。

## 5. 总体切分流程

```text
原始文本
  -> 识别并保护 Markdown 围栏代码块
  -> 普通文本按分隔符栈递归切分
  -> 代码块作为原子片段保留
  -> 合并相邻小片段
  -> 标题与后续内容粘合
  -> 为相邻块添加尾部 overlap
  -> 分配连续 Chunk.id
```

空字符串或空值直接返回空列表。

## 6. 递归分隔符栈

默认分隔符按照从粗到细的顺序排列：

```python
[
    "\n\n",  # 段落
    "\n",    # 行
    "。",     # 中文句号
    "！",     # 中文感叹号
    "？",     # 中文问号
    "；",     # 中文分号
    " ",      # 空格
    "",       # 字符级硬切
]
```

递归规则：

1. 如果当前片段长度不超过 `chunk_size`，直接保留。
2. 使用当前层分隔符切分。
3. 如果文本中不存在当前分隔符，直接降级到下一层。
4. 切分后仍然超长的片段继续使用下一层分隔符递归处理。
5. 到达空分隔符 `""` 时执行字符级硬切。

这种策略优先保留段落和句子边界，只有在自然结构无法满足块大小时才逐步退化。

## 7. 分隔符保留策略

普通字符串切分通常会丢弃分隔符。当前设计将分隔符附加到后一个片段的开头：

```text
输入：第一段。第二段。
按“。”切分后：
  第一段
  。第二段
  。
```

这样在重新合并片段时可以尽量保持原始标点、换行和空格，避免切分造成正文字符丢失。

仅由空白组成的片段会被丢弃；正文片段中的原始分隔符会保留。

## 8. 字符级硬切

当文本没有任何可用的语义分隔符，或者经过所有分隔符处理后仍然超长时，使用固定字符窗口兜底：

```python
text[0:chunk_size]
text[chunk_size:chunk_size * 2]
...
```

硬切保证普通文本最终可以被拆分，但不保证切点位于词、句子或语义边界。

因此空分隔符必须放在分隔符栈最后，只能作为最终兜底。

## 9. Markdown 围栏代码块保护

以下两种围栏代码块会在递归切分前从普通文本中识别出来，并作为不可拆分的原子片段处理：

````markdown
```python
def example():
    return "完整保留"
```
````

```markdown
~~~sql
SELECT * FROM example;
~~~
```

保护规则：

- 开始围栏必须位于行首。
- 支持反引号围栏和波浪线围栏。
- 结束围栏必须与开始围栏类型一致。
- 围栏首行允许携带语言标识。
- 整个代码块作为一个原子片段参与后续合并。

如果代码块自身超过 `chunk_size`，仍保持完整。因此代码块保护的结构完整性优先级高于块长度限制。

当前正则不会保护未闭合围栏、缩进围栏或其他非标准写法。此类内容会进入普通递归切分流程。

## 10. Markdown 标题粘合

当一个普通片段仅包含 Markdown 标题时，切分器会将它与紧随其后的片段拼接：

```markdown
## 混合检索

这里是混合检索的正文。
```

目标是避免产生只有标题、没有正文的检索块。

当前识别范围：

```text
# 一级标题
## 二级标题
...
###### 六级标题
```

标题标记后必须有一个普通空格。标题与后续片段粘合时，结构完整性优先于 `chunk_size`，因此最终结果可能超过配置上限。

## 11. 小片段合并

递归切分会产生多个小片段。合并阶段按原始顺序遍历：

1. 如果当前缓冲区与下一个片段合并后不超过 `chunk_size`，继续合并。
2. 如果合并后超长，将当前缓冲区输出为一个块，并从新片段开始。
3. 代码块可以和前面的普通文本合并，但前提是总长度不超过 `chunk_size`。
4. 标题独立成段时，与后续片段优先粘合。

合并不会改变片段顺序。

## 12. Tail Overlap

合并完成后，为每个非首块添加前一个块末尾的 `chunk_overlap` 个字符：

```text
原块 1：abcdefghij
原块 2：klmnopqrst
overlap = 3

输出块 1：abcdefghij
输出块 2：hijklmnopqrst
```

重叠的作用：

- 保留跨块句子的局部上下文。
- 降低关键信息恰好落在切分边界上的漏召回概率。
- 让向量模型看到前一个块末尾的语义线索。

Overlap 在合并后追加，因此非首块的最终长度可能达到：

```text
chunk_size + chunk_overlap
```

如果前一个块短于 `chunk_overlap`，则复制前一个块的全部内容。

## 13. Unicode 边界

Python `str` 按 Unicode code point 切片，因此不会产生 UTF-16 高低代理项被分开的半字符问题，普通中文字符和单 code point emoji 可以安全保留。

但 code point 不等于用户感知的完整字符。以下组合仍可能被切开：

- 带组合附加符号的字符
- 由零宽连接符组成的 emoji
- 旗帜 emoji 的区域指示符组合
- 某些复杂文字的字素簇

如果业务需要严格保持 Unicode grapheme cluster，应使用字素簇分割库，而不能只依赖 Python 字符串切片。

## 14. 父子块两级切分

RAG 引擎使用同一个 `RecursiveSplitter` 构建父块和子块：

```python
parent_size = max(chunk_size * 4, 600)
parent_overlap = chunk_overlap * 2

parent_splitter = RecursiveSplitter(parent_size, parent_overlap)
child_splitter = RecursiveSplitter(chunk_size, chunk_overlap)
```

处理顺序：

```text
原始文档
  -> 切成较大的父块
  -> 每个父块再次切成较小的子块
  -> 子块用于索引和召回
  -> 保存子块对应的完整父块内容
  -> 命中子块后把父块交给生成模型
```

这种设计兼顾：

- 子块的检索精度
- 父块的上下文完整性

父块自身带 overlap，随后子块又带 overlap，可能产生内容重复。检索融合应按稳定 `pg_id` 去重，生成上下文前还应按父块内容去重。

## 15. 大小单位与模型 Token

当前块大小使用字符数，而不同模型的 Token 划分方式不同：

- 中文字符通常占一个或多个 Token。
- 英文单词可能被拆成多个子词 Token。
- 代码、数字和特殊符号的 Token 密度可能更高。

因此 `chunk_size=200` 不代表固定 200 Token。配置应结合实际 Embedding 模型的 Token 上限和离线语料统计确定。

如果未来改为 Token-aware 切分，应继续保留：

- 递归语义边界优先级
- Markdown 原子保护
- 父子块关系
- 明确的字符或 Token overlap 语义

## 16. 当前实现的边界与加固项

当前实现需要明确以下边界：

1. 代码块和标题粘合可能产生超过 `chunk_size` 的块。
2. 添加 overlap 后，最终块长度可能超过 `chunk_size`。
3. `chunk_size` 按字符计数，不按 Token 计数。
4. 未闭合或缩进的 Markdown 围栏不会被保护。
5. 标题只识别 `#` 到 `######` 加普通空格的形式。
6. Unicode code point 安全不等于 grapheme cluster 安全。
7. 自定义 `separators=[]` 会因为空列表是假值而回退到默认分隔符，不能表示“禁用所有自定义分隔符”。
8. 纯空白片段会被移除，因此切分结果不保证逐字符还原所有原始空白。

可选加固方向：

- 增加 Token 数量预估和上限保护。
- 支持未闭合代码块的保守保护策略。
- 支持缩进代码块和更多 Markdown 标题格式。
- 使用字素簇安全切分。
- 将“原子片段允许超长”设计成明确配置。
- 增加文档类型对应的分隔符配置，例如英文标点和代码语言边界。

## 17. 可观测性

建议记录以下聚合指标，不记录敏感正文：

- 输入文档字符数
- 父块和子块数量
- 块长度的最小值、最大值、平均值和分位数
- 超过 `chunk_size` 的块数量及原因
- 代码块原子数量
- 字符级硬切次数
- overlap 带来的重复字符比例
- 空白片段丢弃数量
- 单文档向量化和索引耗时

这些指标可以帮助判断切分配置是否造成块过碎、块过长或重复率过高。

## 18. 验收标准

至少覆盖以下测试：

1. 空文本返回空列表。
2. `Chunk.id` 从 `0` 开始连续递增。
3. 普通段落优先按双换行切分。
4. 超长段落依次降级到句号、空格和字符级硬切。
5. xxxxxxxxxx 输入：用户问题 + RRF 候选池方法：一次 LLM Listwise 打分主排序：LLM 相关性与信息密度分数稳定兜底：原 RRF 分数 + 原始顺序失败策略：回退 RRF，不中断查询输出：最多 top_k 条精排结果内容限制：每条候选最多 preview_len 个字符调用次数：每次最终检索最多一次精排调用text
6. 分隔符和正文字符得到保留，纯空白片段可被丢弃。
7. 反引号和波浪线代码块保持完整。
8. 超长代码块仍作为单个原子片段保留。
9. 独立 Markdown 标题与后续正文粘合。
10. overlap 为零时不添加重复前缀。
11. overlap 大于等于块大小时被规范化为 `chunk_size - 1`。
12. 相邻块的 overlap 与前一块尾部一致。
13. 普通中文和单 code point emoji 不被破坏。
14. 自定义分隔符按给定顺序递归使用。
15. 父子块关系正确，命中子块后可以回查对应父块。
16. 父块内容在最终生成上下文中正确去重。
17. 明确测试未闭合围栏、缩进围栏和 Unicode 字素簇等边界行为。

## 19. 最终设计边界

```text
输入：原始文本
输出：有序 Chunk 列表
主策略：从段落到字符的递归分隔符栈
最终兜底：字符级硬切
Markdown：代码块原子保护 + 标题正文粘合
连续性：前一块尾部字符 overlap
长度单位：Python Unicode code point 数量，不是 Token
检索策略：子块召回，父块提供生成上下文
超长例外：代码块、标题粘合和 overlap
```
